# 구조와 확장

## 판정과 표현의 분리

브라우저는 `buy`, `sell`, `reroll`, `buyExperience`, `place`, `bench`, `ready`, `equip`, `unequip` 명령을 보내며 체력이나 피해량을 보내지 않습니다. GameRoom이 참가자 소유권, 준비 단계, 서버 마감시각, 슬롯 제한, 점유 칸을 검증합니다. engine.ts는 Phaser나 브라우저에 의존하지 않는 전투 코드입니다.

Colyseus 0.16 계열의 방·입장·재접속을 사용합니다. Schema 대신 100ms마다 접속자별 JSON 스냅샷을 전송합니다. shared/snapshot.ts의 허용 목록으로 본인 정보와 상대 공개 정보를 분리하며 서버 Match를 직접 전송하지 않습니다. 규모 확장 시 변경분 동기화로 교체해도 공개 범위를 유지해야 합니다. 자세한 공개 범위는 PRIVACY.md를 참조하세요. 같은 방의 판정은 서버 한 프로세스에서만 수행합니다.

## 시간

서버는 시작 시의 epoch와 monotonic `performance.now()` 차이로 시계를 만들므로 실행 도중 시스템 시각 조정에 영향을 덜 받습니다. phase deadline은 GameClock의 게임 시각입니다. 기본은 실제 시간과 같은 속도이며, 개발 연습 방에서만 배속·정지할 수 있습니다. 클라이언트는 ping 왕복시간 중간값으로 실제 시각 오프셋을 추정하고 snapshot의 gameNow/serverNow/timeScale로 게임 시각을 계산해 숫자를 표시합니다. 화면 숫자가 0이 되었는지와 무관하게 서버가 명령 접수 시 deadline을 검증합니다.

서버는 100ms 고정 단계로 마지막 시뮬레이션 시각부터 현재 시각까지 전투를 진행합니다. 코스트 회복과 소모는 이 고정 시각을 사용합니다. 네트워크 전송 역시 약 100ms 주기이며 준비 입력의 마감은 서버에서 판정합니다. 스킬 구조와 트리거 동작은 SKILLS.md를 참조하세요.

## 좌표와 모바일

각 참가자의 배치 좌표는 x=0..7, y=0..3입니다. y=0은 후열입니다. 전투 생성 시 서버가 양측 좌표를 하나의 8×8 전장으로 변환합니다. 두 번째 참가자의 화면은 양축을 뒤집어 항상 자신이 아래쪽에 보입니다. 이때 실제 서버 좌표는 변하지 않습니다.

Phaser는 800×800 논리 좌표로 렌더링합니다. 여백은 40, 칸 크기는 90이며 반응형 정사각형 컨테이너와 DOM 칸 버튼이 같은 경계를 사용합니다. 유닛 이미지는 500×500 제작 기준의 정사각형 영역에 원본 비율을 유지해 맞추며, 크기 계산은 client/unit-appearance.ts에서 관리합니다. CSS가 방향에 따라 정보 패널만 재배치합니다. 입력은 DOM pointer 이벤트로 마우스/터치를 통합하며, 클릭/터치 선택과 드래그를 모두 지원합니다. 화면 크기가 바뀌는 중인 드래그는 취소합니다. 터치 드래그가 서서히 스크롤로 바뀌지 않도록 전장에 touch-action:none을 적용합니다.

폰 세로에서 전장 폭을 우선 확보하고 선택 유닛·상세·장비·회수·준비 버튼을 하단 조작 바로 제공합니다. 상세·장비는 명시적 버튼으로 열며 아래 펼침 패널도 유지합니다. 가로의 짧은 화면은 페이지 세로 스크롤을 허용합니다. 핀치 확대는 viewport 설정에서 차단하지 않았습니다. 전장 밖에서 확대/스크롤할 수 있습니다.

## 장비 확장

- EquipmentDefinition: 장비 종류의 이름, 설명, 정적 능력치 보정, 이벤트 훅
- Item: 개별 장비 ID, definition ID, 장착 대상 unitId
- Unit.equipment: 해당 캐릭터에 연결된 Item ID
- statsFor: 강화 체력·공격력을 계산한 뒤 장비 수치를 합산
- Fighter: 라운드 한정 체력·보호막·공격 타이밍. 영구 Unit과 분리

현재 예제는 검(+공격력), 갑옷(+체력), 부적(전투 시작 보호막)입니다. `battleStart`, `beforeAttack`, `afterAttack`, `onHit` 훅을 제공합니다. beforeAttack은 공격자의 피해량, onHit는 피격자의 실제 받을 피해량을 수정할 수 있습니다. afterAttack의 damage는 방어·보호막 처리 후 실제로 줄어든 체력입니다.

새 장비는 catalog의 EQUIPMENT에 추가하고 인벤토리 생성 또는 향후 상점의 지급 코드에 연결합니다. 장착 검증은 반드시 서버 applyAction을 거칩니다. MAX_EQUIPMENT로 슬롯 수를 변경합니다. 장비 희귀도·중복 제한·조합은 별도의 데이터 필드와 서버 규칙으로 추가하세요.

## 배포 방향

현재는 Node 서버가 dist와 WebSocket을 함께 제공하므로 한 서버에서 실행 가능합니다. Ubuntu/Oracle ARM에서도 Node 의존성 설치 후 같은 명령을 사용합니다. `npm ci`에는 빌드 및 tsx 런타임용 개발 의존성도 필요합니다. 실제 운영에서는 서버 TypeScript를 별도 컴파일하거나 tsx 의존성을 배포 구성에 맞게 유지하세요.

HTTPS 역방향 프록시를 쓴다면 WebSocket Upgrade와 적절한 유휴 타임아웃을 설정합니다. 화면과 서버를 별도 도메인에 둘 경우 `.env`의 VITE_SERVER_URL을 공개 HTTPS 주소로 지정하고 다시 빌드합니다. 도메인/방화벽/인증서는 아직 배포하지 않았습니다.

## 자동 합성 (0.6.0)

Unit.rank는 개별 강화 등급, UNITS.rarity는 종류별 가격입니다. 준비 중 구매/획득은 shared/bench.ts의 acquireUnit을 사용합니다. 이 함수는 만석 허용 여부를 판정하고 1성 유닛을 생성한 뒤 shared/merge.ts로 같은 종류의 3개 합성과 3성까지의 연쇄 합성을 처리합니다. 서버가 금액과 상품을 검증한 뒤 성공한 획득에만 결제합니다. 만석에서 잠시 생성되는 임시 유닛은 같은 호출 안에서 합성되어 잘못된 슬롯이 스냅샷에 남지 않습니다.

장비 소유 링크를 남는 유닛으로 이관하거나 null로 반환한 뒤 소모 Unit을 제거합니다. lastMerge는 한 획득의 최종 등급·전체 소모 ID·전체 반환 장비 수이며 본인 알림 전용입니다. Fighter는 새 전투 때 rank를 복사하여 강화 능력치를 계산합니다. 서버 체크포인트도 rank·장비·합성 내역을 보존합니다. 클라이언트는 소모된 선택 ID를 남는 ID로 옮기고 열린 상세 창 가격·장비를 갱신합니다. 새 종류/보상을 추가할 때는 이 공통 획득 경로를 사용해야 합니다.

## 모바일 입력 (0.7.0)

client/interaction.ts의 placementIntent가 터치·드래그의 배치 판정을 통일합니다. 화면 좌표를 각 플레이어 로컬 배치 좌표로 변환하고 출전 정원·점유·대기석 검사를 적용한 뒤 서버 Action을 만듭니다. shared/placement.ts의 순수 계획 함수가 이동/교환/정원/좌표를 검사합니다. 서버는 준비 단계·소유권을 검사한 뒤 동일 계획을 적용하여 두 유닛 위치를 한 명령에서 교환합니다. 선택은 서버 명령이나 상세 창 열기를 하지 않습니다.

GestureClicks는 완료/취소 제스처의 호환 클릭만 포인터 ID·좌표·시각으로 무시합니다. 새로운 pointerdown은 기록을 지우고 detail=0 키보드 클릭은 허용합니다. MutationGate는 한 변경 요청의 본인 준비 상태를 기록하고 의미 있는 본인 상태 변경이나 오류/연결 종료까지 반복 요청을 막습니다. 같은 위치 이동 등 변경 없는 명령은 만들지 않습니다. 변경 없는 정기 스냅샷과 상대 상태 갱신은 응답으로 취급하지 않습니다. SaleConfirmation은 판매 대상 ID·등급·가격에 묶습니다.

main.ts는 바뀐 HTML만 버튼 영역에 적용하여 포인터/키보드 조작 중 불필요한 노드 교체를 줄입니다. 드래그 캡처는 안정적인 body에서 관리하고 비활성 탭·회전·크기 변경·추가 손가락·준비 종료에서 정리합니다. 새로운 연결은 clockAnchor가 설정되는 첫 스냅샷 이전에 편집을 허용하지 않습니다. 자세한 사용법과 미완료 화면 검증은 MOBILE_CONTROLS.md를 보세요.

## 계열 조합 (0.8.0)

`shared/catalog.ts`의 trait과 `shared/synergy.ts`의 TRAITS가 연결됩니다. evaluateSynergies는 단일 팀 출전 목록에서 종류를 중복 제거합니다. startCombat은 실제 정원으로 자른 출전 목록에서 효과를 계산하여 Fighter.stats/시작 shield에 한 번 적용합니다. 원본 Unit에는 능력치나 조합 상태를 저장하지 않습니다. statsFor는 강화된 체력·공격력을 먼저 반올림하고 시너지 배수 적용 후 다시 반올림하며, 마지막에 장비를 가산합니다.

클라이언트는 synergiesForPlayer로 서버가 전송한 공개 범위에서 같은 종류 수를 계산합니다. 준비에는 출전 목록, 전투·결과에는 사망 유닛을 포함한 시작 Fighter 목록을 사용하므로 서버와 동일한 조합을 표시합니다. private 조합 정보나 별도 원본 팀 목록을 전송하지 않습니다. 공개 스냅샷 허용 목록도 유지합니다. 새로운 버전의 클라이언트와 서버를 함께 교체해야 합니다.

## 전투 기록과 접힘 상태

Match.roundHistory는 finish에서 라운드 결과를 추가하고 prepare에서 유지합니다. snapshotFor는 기록을 명시적 허용 목록으로 복사합니다. 디버깅 체크포인트에 기록도 포함되며 newMatch를 사용하는 새 프리셋은 초기화합니다. client/history.ts는 서버 기록과 분리된 조회 상태를 관리하고 history-ui.ts는 상단 중앙의 접힘 버튼/진행표/상세 결과를 표시합니다. 현재 경기의 선택 상태는 탭 저장소에 보관하며 새로고침 시 자동 열기는 하지 않습니다.

## 전투 기여도 (0.11.0)

Fighter.contribution은 시작 시 0으로 생성하고 SkillSystem의 공통 damage 경로에서 실제 HP 감소와 보호막 흡수를 집계합니다. 치유 효과 경로에서 실제 회복량을 source에 집계합니다. 이벤트 배열의 길이와 독립적이며 이 집계로 기존 전투 규칙을 변경하지 않습니다. finish는 m.fighters 전체를 바탕으로 RoundResult.units에 당시 ID/소유자/종류/강화/네 수치를 값으로 복사합니다. 보유 roster나 다음 전투 상태를 참조하지 않습니다. snapshotFor는 완료된 units를 명시적 허용 목록으로 깊게 복사하고 실시간 Fighter 내부 집계는 공개하지 않습니다. client/contributions.ts는 기록만으로 팀별 표시와 숫자 형식을 생성하며 history-ui.ts가 선택된 상세에 연결합니다.

## 최종 결과와 세션 이동 (0.12.0)

Match.endReason은 경기 종료 시 체력 소진/라운드 상한 또는 GameRoom의 연결 종료에서 기록하고 newMatch/prepare에서 초기화합니다. Snapshot은 종료 사유와 방의 실제 연습/대전 mode를 허용 목록으로 공개합니다. 결과 값은 client/results.ts에서 finished와 서버 winner를 바탕으로 계산합니다. 마지막 전투 승자나 문구를 파싱하지 않습니다. FinalResultState는 방/본인/디버깅 세대와 종료 진입을 기준으로 한 번 열며 results-ui.ts의 native dialog와 상단 요약이 조회를 연결합니다. history-ui.openForReview는 선택된 기록을 유지하고 없으면 마지막 완료 기록을 엽니다.

main.ts의 새 경기/로비 이동은 먼저 조작·조회·전장을 초기화하고 명시적으로 기존 방을 떠납니다. 연습은 practice, 대전은 create로 새 방을 시작합니다. Connection은 생성/복원/명시적 떠나기마다 세대를 변경하여 오래된 방 콜백과 늦은 reconnect/restore 응답을 무시합니다. 취소된 요청으로 방이 반환되면 붙이지 않고 떠납니다. 명시적 떠나기는 방 참조/토큰/시간 기준/핑을 비웁니다. 로비는 같은 페이지에서 동작하며 기존 location.reload에 의존하지 않습니다.
